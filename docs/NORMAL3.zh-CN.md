# normal3 参数控制与模板来源

本文记录早期参数与模板实现。2026-09-25 已完成无加热实测，并加入可写的自选食谱、自动熄屏、开盖超时报警、开盖保温超时和完成推送控制；结果与验证边界见 [normal3 无加热实测](NORMAL3_HARDWARE.zh-CN.md)。下文旧版本的实体名称和未实测说明属于当时状态，当前实体以 README 为准，烹饪参数仍需结合日常使用验收。

0.3.0b3支持 `chunmi.cooker.normal3` 的“下次烹饪时长（分钟）”selector、“下次烹饪口感”selector和“下次煮后自动保温”switch。与CMC301共用菜单选择、默认参数初始化、可用性和清空逻辑；协议编码分别实现。原有实体ID、菜单键、启动 `set_start`、停止 `set_func ["end02"]` 和工作状态枚举保留。

这些是下次启动的准备值，修改控件不会立即控制电饭煲。口感仅精煮饭提供偏软/适中/偏硬，默认从食谱自身读取；自动保温仅对能力位允许的菜单可用。未选菜单、启动成功后清空菜单、设备不可达时对应控件不可用；normal3启动失败仍保留选择和参数。选择另一菜单或重新选择同一菜单均恢复该食谱默认参数。

## 官方模板

用户提供的插件1002206 v6，模块10445/11027定义旧式121字节食谱布局及参数写入。模块10130/10133/10562指向官方 `https://gateway.joyami.com` 服务。2026-09-24通过只读GET `/mijia-pot-service/portal/newIndex` 和 `/mijia-pot-service/api/device/optional/{model}/{deviceId}/list`，明确指定用户的normal3设备，取得11份CRC正确的原始 `cookcode`。新版米家v2目录对此型号返回空列表，不能据此推断没有食谱。

内置 `normal3_recipes.json` 只保存模板、菜单和来源信息，不含账号、设备DID或Token；运行时无须登录云端。模板原文保留，参数修改只更改已证实的头部位置并重算CRC。正常烹饪程序区不自行调整。

| 菜单 | recipe键 | 默认分钟 | 可选分钟 | 煮后自动保温可调 |
|---|---|---:|---|---|
| 精煮饭 | jingzhu | 60 | 60 | 是 |
| 快煮饭 | kuaizhu | 40 | 40 | 是 |
| 煮粥 | zhuzhou | 90 | 40–240，每10分钟 | 是 |
| 保温 | baowen | 1440 | 1及10–1440，每10分钟 | 否 |
| 蛋糕 | cake | 60 | 50、55、60 | 否 |
| 酸奶 | yoghurt | 480 | 360–720，每10分钟 | 否 |
| 热饭 | refan | 30 | 30 | 是 |
| 蒸煮 | cooking | 30 | 10–60，每5分钟 | 是 |
| 米饭 香甜煮 | sweet_rice | 70 | 70 | 是 |
| 糙米饭 | brown_rice | 105 | 105 | 是 |

最新取得的normal3热饭模板上下限均为30，因此只提供30；CMC301再加热仍是25/30/35。范围跨度不超过60分钟用5分钟步长，超过60分钟用10分钟步长，保留上下限及默认值。固定时长也有一个可用选项，并自动选中。服务 `start_recipe` 同样支持normal3的时长、口感和自动保温，但时长服务参数允许范围内的整数分钟，不局限于UI选项；normal3 也支持预约准备参数，具体时间换算与验证边界见下节。

## 兼容与验证

11份模板中有多份加热程序与旧仓库版本不同，本次使用该型号当前官方服务返回值，并非只修补旧CRC。原有9个菜单键保留，末尾增加糙米饭和炖汤；当前/收藏菜单传感器补充这两个菜单及香甜煮的识别，原有工作状态枚举不变。其他老型号继续使用原有 `cooker_profiles.json`，没有套用normal3食谱。

0.3.0b5共169项自动化测试通过，覆盖CRC、参数边界、精煮口感与时长复用字节、加热程序保持、菜单/选项/默认值同步更新、断线与恢复、成功清空及失败保留、其他型号隔离，以及阶段解析与兼容性。另外执行提供的官方JS编码器，对11份模板的37组默认/边界/口感/保温组合进行对照，输出报文逐字节一致。新增参数和更新后的normal3食谱尚未在实机及用户HA环境验收；后续随日常做饭核对，不把离线验证称为实机成功。

两种型号均使用新的时长select实体。升级时只移除同一设备、同一配置项下旧的时长number注册；原有菜单和反馈实体保留。若曾使用0.3.0b0–b2的时长number自动化，请改用 `select.select_option`（option如 `"90"`）或原子的 `xiaomi_miio_cooker.start_recipe`。

## 阶段名称与说明（0.3.0b5 修正）

原实现使用python-miio对原始 `stage` 的通用映射，其中有英文拼写错误、语句截断和机型适用性问题。0.3.0b5改用提供的normal3官方插件11030/10904的判断方式：仅在精煮饭、快煮饭正在烹饪（原始 `func=running`）时，去除温度历史前两个头部字节，再按 `AA` 分隔符数量识别五阶段。与CMC301共用阶段枚举和完整的中英文名称、说明，不再读取normal3的依赖库通用阶段文案。

| 状态枚举 | 中文阶段名称 |
|---|---|
| `quick_preheat` | 快速预热 |
| `water_absorption` | 中温吸水 |
| `boiling` | 大火煮沸 |
| `gelatinization` | 高温糊化 |
| `simmering` | 焖饭补炊 |

两个实体的ID保留，原生状态均为上述稳定枚举，HA按语言分别显示阶段名称和完整说明。**依赖旧英文状态文本的自动化条件需要更新为枚举值**；旧原始阶段码与新枚举之间不能套用一张通用对照表。其他老型号继续使用其原有阶段显示，未套用normal3的规则。

属性 `source=temperature_history`、`history_based=true` 标明来源；`phase_index` 是历史分段索引，`stage_code` 和 `raw_stage` 仍为独立的设备原始反馈，不能混为一谈。原有米种、口感等数值字段保留。原始stage缺失或格式异常不再连带丢失总体状态，有有效历史时仍可显示阶段。

空历史、只有分隔符、格式异常或分段索引超出范围均显示未知；预约、待机、保温和其他食谱也不显示这五阶段，不猜测未知原始阶段码。运行中的这两种米饭每30秒刷新历史，模式/菜单变化及启动、停止后清除缓存；历史读取失败不会继续显示旧阶段。上述边界已有离线测试，normal3实际完整阶段切换仍需日常做饭时验收；本轮没有启动加热。

## 预约时长（2026-09-27）

原插件 11027 使用手机 `new Date().getHours()/getMinutes()` 加上预约时长，超过午夜则折回次日；启动调用链没有读取设备时区或校时。模块 10445 将启用位与完成小时写入第 9 字节、完成分钟写入第 10 字节，并保留自动保温位。设置页的设备时区入口不参与这条计算链。

集成以 HA 配置时区替代手机时区，在取得设备锁并确认待机后才计算完成时刻。预约须大于烹饪时长、最多 1439 分钟；跨夏令时切换或落入重复/不存在的本地时刻会被拒绝。HA 与设备应配置相同的时区。预约启动不自动重试，结果不确定时清空准备选择，避免重复启动。

精煮、快煮、煮粥、cooking、sweet_rice、brown_rice、soup 的当前模板支持预约；保温、蛋糕、酸奶、再加热不支持。UI 控件与 start_recipe 服务共用校验与编码。原版插件编码对比及异常路径使用离线测试；实机预约接受、倒计时和取消仍待验证，本轮未启动设备。

预约反馈沿用插件 11030 的 renderPreparing：t_precook 是完成钟表时刻，不是依赖库说明中的等待分钟数。预约期间 Remaining time 用此值与 HA 本地时钟换算，支持跨午夜以及插件识别的次日值；无有效时刻或跨夏令时歧义则为 unknown。它不依赖从 HA 发起预约，因此也适用于面板和米家启动的预约。Current duration 仍是 t_cook 的烹饪时长，未将其冒充最初预约总时长。
