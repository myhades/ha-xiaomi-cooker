# CMC301 本地集成与验证

当前实现使用独立 MIoT 后端，不需要运行时登录小米账号。设备须可通过 UDP 54321 访问；跨 VLAN 能 ping 通并不保证该通道可用。添加设备时自动识别型号，Token 支持清理 BOM 和复制产生的空白。

## 实体交互与字段含义（2026-09-26）

烹饪菜单的 `none` 选项显示“未选择”，用于初始化及取消准备。开始后菜单、口感和时长选择器禁用；当前菜单、当前口感、当前时长由独立传感器读取，待机时不把最后一次读数冒充当前任务。停止按钮仅在烹饪、预约或保温中可用。自选食谱的候选项始终保留，运行时只禁用控件；尚未读到自选槽时仍显示未知。

有限文本状态通过 Home Assistant 的 `options` 和 `SensorDeviceClass.ENUM` 暴露，选择器本身通过 `options` 暴露。数值时长、温度不伪装为枚举。旧版本 v0.1.0/v0.2.0 的 coordinator 以 Python `None` 初始化和清空选择，没有独立取消选项；HA 状态机会把它表示为 `unknown`。

故障依据本型号 MIoT 定义属性 2.2，以及官方插件 1041640 v1 模块 10187/10856：0 无故障、5 顶部传感器故障、6 底部传感器故障、7 通信故障。未列出的整数显示“其他故障”，原始数字保留在 `code` 属性中；未读到值时保持未知。

完成推送依据模块 10187 的 `cookFinishPush`/`cookFinishPushMsg`，以及 10196 的 `get_setting`/`set_setting`：设置串第三字节 00 开启、01 关闭烹饪完成消息推送，与蜂鸣器属性 2.32 分开。normal3 插件 1002206 v6 的 10010/10448 模块也把本地保存的推送开关传给 `set_setting` 的 `en_push` 参数。这是设备端控制米家推送的设置，不是 HA 通知；本轮没有验证手机送达。

水已煮开依据模块 10856 属性 2.29 → `boil`，以及 10859 在工作状态且 `boil` 为真时显示模块 10187 的“水已煮开，可以放面啦”提醒。它是烹饪流程标志，不应解释成持续检测水当前是否正在沸腾；也没有证据表明每个菜单都产生这个标志。本轮仅审查源码，没有启动加热或人为制造故障。

## 操作

1. 在“烹饪菜单”选择菜谱。选择菜单只准备参数，不发送加热命令。
2. 调整可用的“时长”“口感”“自动保温”“预约时长”。切换菜单会恢复该菜单模板的默认值；HA 重启后需要重新选择。
3. 点击“开始烹饪”。预约倒计时单位为分钟，表示从点击开始到预计完成的时间，0 表示立即启动。预约必须长于烹饪时长；超快饭还按官方页面规则预留 12 分钟。
4. “停止烹饪”是独立命令，不依赖已选菜单。启动前会读取待机、故障和远程控制许可；停止不受远程许可状态拦截。

从0.3.0b3起，“时长”改为 selector：范围跨度不超过60分钟时按5分钟分段，更大范围按10分钟分段，并额外保留合法上下限和模板默认值。再加热为25/30/35，煮粥为40/50/…/240；超快饭固定28分钟，仍有一个可用选项。菜单、时长选项和默认选中值一次更新，启动清空或未选菜单时不可用。升级会移除同一设备旧的 `number.*next_duration` 注册；使用旧 number 实体的自动化需改为对新 select 调用 `select.select_option`，或者直接使用 `start_recipe`。

“自动保温”同时受设备可用性和当前“烹饪菜单”约束：未选菜单、所选菜单不支持煮后保温或设备不可达时，开关显示不可用。它是本次食谱的准备参数，不是运行中随时切换的设备开关。开始后菜单和准备参数一起清空，开关随之不可用；断线恢复不会擅自重置尚未发送的选择，重新加载集成则从未选择状态开始。

两种型号共用菜单选择与清空逻辑，保留原有 selector 实体。normal3 仍在启动成功后清空、失败后保留选择；CMC301 为避免响应丢失造成重复启动，在发送前就清空。命令执行期间新选的菜单（即使与刚启动的相同）不会被旧命令完成时清掉。

“自选食谱”选择器直接将所选内置食谱及默认参数保存到面板，不会启动，也不依赖烹饪参数选择器。设备处于自选模式时读取食谱编号；已识别但不在内置列表中的显示“其他”，禁止选择“其他”。尚未观察到自选内容时显示未知；离开自选模式后保留最近读回，重新加载则需重新确认。

自动化可以使用 `start_recipe` 一次提交参数，避免分别修改多个准备实体；原有 `start(profile)` 服务保留。

## 反馈与设置

- 实际反馈：工作状态、模式、食谱、目标分钟、剩余分钟（从设备秒数换算）、故障代码、设备口感、食谱类型、远程许可、水沸腾。
- 诊断反馈：原始状态/模式、食谱编号、重置同步标志、有效温度历史样本数。
- “温度”来自历史串最后一个有效样本；按官方插件规则，短于三个字节的响应不会产生温度，解析跳过前两个字节及 AA 阶段标记。它不是即时温度；米饭运行中的阶段反馈和运行中空历史使用30秒读取间隔，其余已有样本约两分钟刷新一次，状态、菜单或故障变化时重新读取。
- 设置：自动熄屏选择器提供关闭、2至10分钟（间隔1分钟），另有完成推送和食谱指示灯选择器。熄屏开关与时长在同一命令中写入，保留其他设置并读回核验。
- 全部模式显示开启表示所有模式亮起、选中模式闪烁；关闭表示仅选中模式亮起。

菜单、时长和口感选择器用于准备参数，运行时不可用，设备反馈由当前菜单、当前时长和精煮口感传感器提供。精煮口感选择器仅在选中精煮饭且未开始时可用，默认中等；其他菜单时不可用。基础模式不再单独创建实体，原始值留在诊断数据中。尚未发现可靠的自动保温开关读回、米种控制、实际功率或锅盖状态接口，不提供虚构实体。完成推送位能写入，并不保证未登录云服务时仍能收到手机通知。完成事件、保温来源与分钟计时见[实体对照](ENTITIES.zh-CN.md)。

## 烹饪阶段（0.3.0b4）

新增 `stage_name` 与 `stage_description`。官方插件1041640 v1的10856/10871模块只在食谱ID1（超快饭）、2（精煮饭）运行中显示温度曲线阶段；10610模块跳过历史前两字节后，按 `AA` 分隔符数量选择以下五阶段及对应说明：

| 阶段码（分隔符数） | 稳定状态键 | 中文显示 |
|---|---|---|
| 0 | quick_preheat | 快速预热 |
| 1 | water_absorption | 中温吸水 |
| 2 | boiling | 大火煮沸 |
| 3 | gelatinization | 高温糊化 |
| 4 | simmering | 焖饭补炊 |

两个实体使用同一稳定状态键，前端分别翻译为名称和说明，支持中英文；不是设备直接返回的文字。属性 `source=temperature_history`、`history_based=true`、`stage_code` 标明来源。不要把其阶段码直接等同于normal3的原始stage编码。

其他食谱没有已确认的这套阶段映射，继续使用总体工作状态和剩余时间；并不表示其烹饪过程没有物理阶段。预约、保温、完成、故障、待机时不沿用旧阶段。空历史、只有分隔符、非法十六进制或超过已知阶段范围均显示未知，不像插件那样将缺少数据默认当成预热。阶段随历史读取更新，不能代表瞬时加热器通电状态。

解析、状态切换与缓存失效已做离线测试；尚未在真实完整烹饪过程中核对五阶段逐项切换，本次实现未追加加热测试。

## 兼容与验证边界

normal3 的启动/停止 RPC、原有实体唯一标识、既有菜单键和工作状态枚举保持兼容；已有温度历史解析和缓存修复保留。0.3.0b3新增共用的时长、口感和自动保温控件，使用从旧插件官方服务取得的11份有效食谱，替换旧 CRC 不一致模板并补充糙米饭、炖汤。此食谱更新仅适用于normal3，不改变其他老型号模板，详见[normal3说明](NORMAL3.zh-CN.md)。

本地读属性、设置、默认模式启动/停止有此前设备探测依据。完整食谱 action 2.6 的立即启动、预约、目标时长和口感反馈现已实测；面板自选 action 2.5 也已保存煮粥130分钟并读回一致参数。超快饭28分钟完整周期后自动进入保温，已获用户现场确认。详见[实机记录](HARDWARE_VALIDATION.zh-CN.md)。关闭自动保温后的结束行为、其他菜单逐项完整执行和 HA 实际部署仍未验收。

开始命令不自动重发；响应丢失会报错并刷新状态，界面选中项也会清除。应先查看设备实际状态再重新选择并操作。未公开原始食谱服务的任意加热程序支持。

“预约烹饪中”是设备原始状态，不代表可以判断加热器是否正在通电。其余菜单和关闭自动保温后的行为可在日常使用中继续核对，不必为了检查每个实体重复短时开关加热。
